# 配方发布与回滚设计改进（2026-10-20）

本轮处理发布前的差异核对、发布失败反馈、多人并发确认和配方列表请求生命周期。

## 问题与改进

| 原设计问题 | 影响 | 改进 |
| --- | --- | --- |
| 发布确认固定比较目标版本的上一版本；回滚 V1 比较 V1 与自身 | 生效 V3 回滚到 V1 时显示无变化；跳过中间草稿发布也看不到实际影响 | 打开确认框重新读取配方，比较“当前生效版本 → 目标版本”；首次发布明确没有生效基线 |
| 差异读取失败仍允许确认 | 无法审查变更也能继续发布 | 配方或差异读取失败时禁止确认，提供重新核对入口；校验响应对应的配方和版本 |
| 静态确认框的 onOk 调用会吞掉错误的通用 invoke | 后端拒绝发布，确认框仍关闭，容易被理解为成功 | 独立的受控确认组件持有核对与提交状态；失败保留窗口，展示错误、错误码和关联 ID |
| 确认所用快照与事务提交之间没有并发检查 | 其他人已经切换生效版本，旧确认仍可能覆盖新发布 | 请求携带原始 updatedAt；在 SQLite 即时写事务内检查修订，不符返回 409，必须重新核对 |
| 只比较生效版本号无法识别 V1 → V2 → V1 | 很早的核对可能在版本号回到 V1 后再次被当成有效 | 使用修订时间而非生效版本号；每次发布修订严格递增，包括时钟分辨率不足或回拨时 |
| 提交只靠 React 展示状态避免重复 | 同一事件中连续触发可重复写入发布历史 | 同步 ref 阻止重复提交；提交期间禁用关闭、取消和重新核对 |
| 请求超时、网络断开或成功响应无效时缺少不确定状态 | 后端可能已提交，用户直接重试会重复发布 | 明确提示结果未确认，禁止直接重提，要求重新读取生效版本；不自动重试写请求 |
| 回滚入口允许选择未生效情况下的版本或更高版本 | 回滚含义与实际切换方向不符 | 菜单与确认框都要求目标早于当前生效版本；已生效或验证未通过的版本禁止确认 |
| 配方列表读取没有取消与请求代次 | 关闭重开或连续刷新后，旧正文可覆盖新列表，旧请求也可能提前解除加载状态 | 后续刷新取消先前读取，读取正文后核对代次与挂载状态；关闭即取消，15 秒超时可重试 |

## 接口与兼容性

- `POST /api/jobs/{id}/versions/{version}/publish` 和 `POST /api/jobs/{id}/rollback/{version}` 新增可选查询参数 `expectedUpdatedAt`。
- 前端直接编码后端返回的原始 ISO 时间字符串，保留七位小数精度，不经过 JavaScript Date 的毫秒转换。
- 检查发生在更新生效版本、保存依赖清单和追加发布历史之前；检查失败不产生发布记录。原有编译与验证策略仍生效。
- 不需要数据库迁移。旧客户端不传参数时保留原有行为；新前端的并发保护需要配套更新后端。
- 确认框刷新后如果发现目标已生效，显示无需重复发布。关闭确认框会刷新配方列表，帮助核对结果未确认的提交。
- 版本菜单里的“与上一版本对比”仍用于人工浏览历史，不作为发布核对的基线。

## 验证

- 前端专项覆盖实际生效版本对比、首次发布、验证与回滚方向、差异错误、失败留框、同步重复点击、时间精度、冲突后重新核对、不确定提交、慢正文、卸载、超时及配方管理集成。
- 后端覆盖相同修订的并发竞争、旧修订拒绝且不追加历史、生效版本往返、时钟回拨、时区等价、两个端点的参数转发与旧客户端兼容性。
- 所有测试使用模拟网络或临时数据库与合成图像流程，不连接现场设备。

验证结果：前端专项 24 项通过，全量 52 个文件、723 项测试通过；后端发布并发、配方生命周期和 OpenAPI 相关回归 15 项通过。TypeScript、生产构建、静态审计和 diff 格式检查通过；构建仍有现有的大包体积提示。
